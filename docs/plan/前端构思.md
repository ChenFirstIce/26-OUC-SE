# 阿尔茨海默病评估系统——患者端整体方案说明

## 一、整体开发思路

整个课程项目分为两条相对独立的系统线：

```text
医生系统
医生/管理者使用
负责患者管理、医学信息查看、评估结果查看等

                ↓ 后期通过接口衔接

患者系统
患者使用
负责接收评估任务、完成量表、完成认知测试、
提交结构化评估数据
```

现阶段两边**不做强耦合开发**。

也就是说，患者团队暂时不需要等待医生端完成：

> 医生登录 → 选择患者 → 选择量表 → 派发任务

这一整套流程。

患者端内部自己增加一个非常轻量的：

> **管理员 / 测试模式**

用于模拟“医生已经完成派发”。

这样患者端可以自己完成完整闭环：

```text
管理员选择患者
        ↓
选择一个或多个评估任务
        ↓
点击“派发”
        ↓
患者进入自己的任务中心
        ↓
看到待完成量表
        ↓
完成评估
        ↓
系统计分 / 记录交互数据
        ↓
提交患者后端
        ↓
查看完成状态
```

这个管理员页面的目的**不是重新做一套医生系统**。

它只是患者端的：

> **任务配置工具 + 测试入口**

后期真正和医生端联调时，再把这个管理员派发过程替换成医生端 API 即可。

------

# 二、为什么采用两条独立系统线

这样做主要解决三个问题。

### 1. 避免互相卡进度

如果患者端必须等待医生端完成：

```text
患者管理
↓
任务创建
↓
量表派发
↓
患者接收
```

那么医生端稍微晚一天，患者端大量功能都没办法测试。

现在患者团队自己就能：

```text
Admin → 派发 → Patient → 答题
```

完全独立运行。

------

### 2. 课程展示更稳定

即使最后医生端和患者端接口联调存在问题，我们仍然可以直接展示：

```text
管理员派发 GDS-15
↓
患者首页出现任务
↓
患者完成量表
↓
自动计分
↓
提交结果
```

整套患者业务是完整的。

------

### 3. 后期仍然可以对接医生端

虽然开发阶段独立，但数据结构要提前统一。

真正需要两边约定的其实只有几个核心 ID：

```text
patientId
assessmentId
assignmentId
status
submission
```

以后医生端只需要生成：

```json
{
  "patientId": "P001",
  "assessmentId": "GDS15",
  "assignmentId": "A001"
}
```

患者系统本身不需要重新设计。

------

# 三、患者端的系统定位

我们患者端主要负责的不是“疾病诊断”，而是：

> **完成患者侧认知评估任务的交互、数据采集、初步量化和结果提交。**

患者端主要完成四件事情：

```text
① 显示
把量表 / 认知测试展示给患者

② 交互
让患者完成选择、输入、连线、看图命名、对话等任务

③ 量化
把患者操作转换成结构化数据

④ 提交
把原始回答、得分和过程指标交给后端
```

所以患者前端最终输出的不应该只有：

```text
GDS = 6分
```

最好同时保留：

```text
原始回答
每题得分
总分
完成时间
答题时长
错误次数
提示使用情况
连线顺序
对话记录
```

你们原始需求中也明确要求“保存量表填写结果”和“将量表数据结构化保存”。

------

# 四、患者端整体页面结构

我建议患者系统最后只有四个核心区域。

```text
患者系统
│
├── ① 登录 / 身份选择
│
├── ② 患者任务中心
│     ├── 待完成
│     ├── 进行中
│     └── 已完成
│
├── ③ 评估中心
│     ├── A类：普通结构化量表
│     ├── B类：特殊认知交互任务
│     └── C类：LLM问答任务
│
├── ④ 完成页 / 历史记录
│
└── ⑤ 管理员模式
      ├── 选择测试患者
      ├── 选择量表
      ├── 批量派发
      ├── 重置任务
      └── 查看提交数据
```

其中真正工作量最大的就是：

> **③ 评估中心**

# 五、量表不应该一张一张单独开发

这是患者端整个技术设计里最重要的一点。

我们不应该：

```text
GDSPage
ESSPage
SCDQ9Page
RBDSQPage
PSQIPage
……
```

每个量表重新写一套。

而是实现一个：

# 通用量表渲染器 Assessment Engine

结构类似：

```text
              Assessment Engine
                     │
       ┌─────────────┼─────────────┐
       ↓             ↓             ↓
   是非题组件      单选组件       多选组件
       ↓             ↓             ↓
   数字输入        等级评分       日期时间
```

每套普通量表只需要提供：

```text
量表名称
量表介绍
题目
选项
题型
计分规则
```

例如：

```json
{
  "id": "gds15",
  "name": "GDS-15",
  "questions": [
    {
      "id": "q1",
      "type": "boolean",
      "text": "题目内容",
      "scoreRule": {}
    }
  ]
}
```

前端自动渲染。

因此新增一个普通量表：

> 主要是在增加数据，而不是重新开发页面。

这个设计也非常适合作为课程答辩里的一个软件工程亮点：

> **配置驱动、组件复用、量表与页面逻辑解耦。**

------

# 六、我们最终选择哪些量表

根据目前整理出来的量表，原文件已经把患者相关内容划分为了三类：

- A：患者/知情者可以直接填写；
- B：不需要 LLM、通过普通程序即可辅助完成；
- C：需要 LLM 对开放语言或访谈内容进行辅助判断。

考虑：

> 开发时间 + 技术覆盖面 + 最后展示效果

我建议患者端最终完成以下内容。

------

# A 类：普通结构化量表

## 必做 1：GDS-15

**形式：**

```text
是 / 否
```

这是最适合验证通用问卷系统的一套量表之一。

患者界面可以做成：

```text
问题 4 / 15

████████░░░░░

       [题目]

┌─────────────┐
│      是      │
└─────────────┘

┌─────────────┐
│      否      │
└─────────────┘

上一题             下一题
```

前端需要输出：

```text
15题答案
每题得分
总分
完成时间
```

------

> **0—3 级选择。**

它正好可以用来测试我们的：

```text
┌──────────┐
```


> - 爱丁堡利手量表

# 七、B 类：非 LLM 特殊交互任务

B 类不要做太多。

这里的主要意义不是堆数量，而是证明：

> 我们的患者端不仅能做普通问卷，也可以实现认知评估中的特殊交互。

最终选两个。

------

# B 类必做 1：Boston 命名

原方案中 Boston 命名涉及：

> 展示图片、计时、识别命名答案、按照规则给予提示、生成初步分数。

患者端实现：

```text
              题目 5 / 10

          这是什么物品？

     ┌─────────────────┐
     │                 │
     │      图片       │
     │                 │
     └─────────────────┘

您的回答：

┌─────────────────────┐
│                     │
└─────────────────────┘

当前用时：00:08

[需要提示]              [提交]
```

前端输出：

```json
{
  "answer": "患者回答",
  "durationMs": 8000,
  "hintUsed": false,
  "score": 1
}
```

这个任务展示效果会很好。

------

# B 类必做 2：STT 形状连线

资料中对 STT 的描述是：

> 自动记录连线顺序、轨迹、错误和用时，主要属于规则程序。

这正好可以做成患者端最有特色的页面之一。

例如：

```text
1 → A → 2 → B → 3 → C
```

患者点击：

```text
1
↓
A
↓
2
↓
B
……
```

前端实时：

```text
记录点击顺序
绘制连线
统计时间
判断错误
```

最终输出：

```json
{
  "sequence": ["1", "A", "2", "B"],
  "durationMs": 46210,
  "errorCount": 1,
  "completed": true
}
```

# 八、C 类：LLM 辅助任务

C 类主要为了体现整个项目的 AI 扩展能力。

但患者前端团队不用负责模型本身。

患者端只负责：

> **提供交互界面 + 调用 LLM API + 展示返回内容。**

------

# C 类必做 1：SCD 结构化访谈

资料中设计的是：

> 根据认知下降表现、起病时间、担忧和就医情况进行动态追问。

患者界面可以直接设计成聊天模式：

```text
AI
最近有没有感觉自己的记忆力
相比过去出现明显变化？

                   患者
有时候会忘记刚刚把东西放在哪里。

AI
这种情况大概从什么时候开始出现？
```

患者前端只需要：

```text
发送 message
↓
后端 / LLM
↓
返回 reply
↓
继续展示
```

最终保存完整 Conversation。

------

# C 类必做 2：MoCA-B 开放题

原设计中 LLM 可以用于：

> 判断抽象分类、付款方案等不同合理表达。

这里可以设计一个：

```text
开放回答题
      ↓
患者输入自然语言
      ↓
提交
      ↓
“正在分析回答……”
      ↓
LLM返回候选判断
```

患者页面不必告诉用户：

> AI 给了你 0 分。

患者只显示：

> ✓ 回答已记录

评分信息在后台数据里保存即可。

# 十二、我们目前的 MVP 边界

这个尤其建议你们团队统一认识。

你们原始周报定义的 MVP 是：

> 第一阶段实现 A 类量表和基础功能；第二阶段设计非 LLM 标准化交互；第三阶段尝试接入 LLM。

所以现在可以把验收优先级定义成：

### P0：必须成功

```text
管理员派发
↓
患者看到任务
↓
GDS / ESS / SCD-Q9 可以答
↓
自动保存
↓
完成
↓
生成结构化数据
↓
成功提交
```

### P1：展示亮点

```text
Boston 图片命名
STT 连线
```

### P2：AI 扩展

```text
SCD AI 访谈
MoCA-B 开放回答
```

也就是说：

> **就算 AI 最后接入出现问题，只要 P0 + P1 做完整，我们的患者端依然是一个完整且有特色的课程项目。**

而如果 P2 也接通，那么它就是展示时最大的 AI 亮点。

------

我现在最建议你们患者团队统一的一句话是：

> **患者端不是“做很多张量表页面”，而是开发一个可配置的认知评估平台：通过通用 Assessment Engine 支持普通量表，通过独立 Task Component 支持特殊认知测试，通过统一 AI Interaction Interface 支持 LLM 辅助评估；同时提供轻量管理员模式模拟任务派发，使患者端可以脱离医生端独立运行和演示。**

这句话其实也可以直接放到你们之后的软件工程实践报告里。
