# 第一阶段 MVP：全 Web 量表录入与计分闭环

## 1. MVP 目标

在 2026 年 9 月 17 日前完成以下程序闭环：

```text
医生通过管理 Web 创建受检者与评估
              ↓ 生成二维码链接和备用评估码
患者通过手机 Web 填写量表
              ↓ 服务端保存并自动计分
医生通过管理 Web 查看报告和基础统计
```

首期功能：

- 受检者基础档案。
- SCD-Q9、GDS-15 两张量表。
- 二维码链接和 8 位备用评估码。
- 草稿自动保存和恢复填写。
- 服务端规则计分。
- 医生查看结构化报告。
- 受检者数、完成评估数、两张量表平均分。
- 单一医生演示账号。
- 编号化虚拟数据。

本阶段只聚焦程序设计、开发、测试和运行，不安排 PPT、实践报告、视频等最终交付物。

## 2. 系统结构

系统由两个独立 Web 前端、一个共享后端和一个数据库组成：

```text
患者移动端 Web ─┐
                 ├── 统一后端 API ── 数据库
医生桌面端 Web ─┘
```

建议工程边界：

```text
patient-web/   患者移动端 Web
admin-web/     医生桌面端 Web
server/        后端服务
contracts/     API 文档、公共类型和错误码
```

两个 Web 前端分别构建，通过同一个后端 API 和统一接口契约联调。四名后端成员必须使用同一个后端工程和数据库，不拆分微服务。

## 3. 技术栈确定机制

暂不指定具体前端、后端和数据库框架。开发前根据七名成员的实际经验完成选型。

选型要求：

- 至少两人能够维护移动端 Web。
- 至少两人能够维护后端。
- 支持响应式网页和 JSON API。
- 支持自动化测试。
- 能在演示电脑上快速启动。
- 尽量减少团队需要临时学习的新技术。

技术栈确定后，应记录：

- 语言、框架和版本。
- 项目目录结构。
- 依赖安装和启动命令。
- 数据库初始化方式。
- 开发环境配置方式。
- 各工程负责人。

技术栈确定后，本阶段中途不再更换框架。

## 4. 患者答题 Web

患者端采用移动优先设计，主要支持手机浏览器和微信内置浏览器。

### 页面与路由

- `/`：输入备用评估码。
- `/assessment/{token}`：通过二维码进入指定评估。
- `/assessment/{token}/intro`：确认受检者代称和非诊断提示。
- `/assessment/{token}/scale/{scaleCode}`：填写量表。
- `/assessment/{token}/review`：检查漏答并确认提交。
- `/assessment/{token}/success`：提交成功。

### 主要功能

1. 扫描二维码或输入备用评估码进入任务。
2. 展示受检者代称、量表列表和非诊断提示。
3. 分步骤填写 SCD-Q9、GDS-15。
4. 显示当前题号和总体进度。
5. 选择答案后自动保存草稿。
6. 刷新或退出后恢复未完成答案。
7. 提交前检查漏答并定位未完成题目。
8. 提交后展示成功状态并锁定任务。

评估状态固定为：

- `CREATED`：尚未填写。
- `IN_PROGRESS`：存在草稿。
- `SUBMITTED`：已提交并锁定。

交互要求：

- 以 360–430px 手机屏幕为主要适配范围。
- 选项和按钮尺寸适合老年用户点击。
- 网络失败时保留当前本地答案并提示重试。
- 不向患者展示疾病诊断结论。

首期不实现患者注册、微信授权、消息通知、PWA 安装、离线提交和患者报告查询。

## 5. 医生管理 Web

### 页面与路由

- `/login`：医生登录。
- `/dashboard`：基础统计。
- `/patients`：受检者列表和创建入口。
- `/patients/{id}`：档案及评估历史。
- `/patients/{id}/assessments/new`：创建评估。
- `/assessments/{id}`：评估状态、二维码和备用码。
- `/assessments/{id}/report`：答案及计分报告。

### 主要功能

- 单一医生账号登录。
- 创建和查看受检者档案。
- 创建评估并生成二维码链接和 8 位备用码。
- 查看评估状态。
- 查看逐题答案和量表总分。
- 展示受检者数、完成评估数和量表平均分。

受检者档案只包含：

- 编号。
- 代称。
- 性别。
- 出生日期。
- 受教育年限。
- 备注。

管理端页面保持 MVP，不实现复杂图表、分页组件封装、主题切换、批量操作、导入导出、多医生权限和精细动画。

## 6. 后端与数据设计

### 核心数据对象

- `User`：单一医生账号和密码摘要。
- `Patient`：受检者基础档案。
- `Assessment`：受检者、二维码令牌、备用码、状态和时间。
- `Response`：量表编号、版本、JSON 答案和更新时间。
- `ScoreResult`：总分、逐题得分、计分版本和生成时间。

答案统一采用可扩展结构：

```json
{
  "scaleCode": "SCD_Q9",
  "scaleVersion": "1.0",
  "answers": {
    "Q1": "YES",
    "Q2": "NO"
  }
}
```

二维码令牌使用至少 128 位安全随机值。备用评估码使用排除易混淆字符的 8 位随机字符串。令牌和备用码在评估提交后失效。

### 医生端 API

- `POST /api/auth/login`
- `GET /api/patients`
- `POST /api/patients`
- `GET /api/patients/{id}`
- `POST /api/patients/{id}/assessments`
- `GET /api/assessments/{id}`
- `GET /api/assessments/{id}/report`
- `GET /api/dashboard/summary`

### 患者端 API

- `POST /api/public/assessments/resolve`：使用备用码获取访问地址。
- `GET /api/public/assessments/{token}`：读取任务、题目和草稿。
- `PUT /api/public/assessments/{token}/responses`：幂等保存草稿。
- `POST /api/public/assessments/{token}/submit`：校验、计分并提交。

创建评估的响应至少包含：

```json
{
  "assessmentId": 12,
  "accessUrl": "http://192.168.1.10/patient/assessment/随机令牌",
  "shortCode": "7KD9MX2Q",
  "status": "CREATED"
}
```

统一错误码：

- `INVALID_CODE`：评估码或令牌无效。
- `ASSESSMENT_SUBMITTED`：评估已经提交。
- `INCOMPLETE_RESPONSES`：存在未答题目。
- `UNAUTHORIZED`：医生未登录或登录失效。
- `VALIDATION_ERROR`：字段格式错误。
- `NETWORK_ERROR`：患者端保存请求失败。
- `INTERNAL_ERROR`：服务端异常。

最终提交必须在同一事务内完成答案保存、计分、结果保存和状态更新。前端不得提交或修改分数。

## 7. 计分规则

### SCD-Q9

- 第 1、2、3、6、8、9 题：“是”1 分，“否”0 分。
- 第 4、5、7 题：“经常”1 分，“偶尔”0.5 分，“从未”0 分。
- 总分范围：0–9。

### GDS-15

- 回答“是”计分：2、3、4、6、8、9、10、12、14、15。
- 回答“否”计分：1、5、7、11、13。
- 每项命中计 1 分，总分范围：0–15。

计分只允许在后端执行。原材料没有给出足够明确的诊断阈值，因此首期只展示分数和逐题结果，不自动诊断 AD 或抑郁程度。

## 8. 七人模块分工

采用“答题前端 2 人、答题后端 2 人、管理前端 1 人、管理后端 2 人”的分配。

| 人员 | 模块 | 主要职责 | 明确所有权 |
| --- | --- | --- | --- |
| A | 答题前端基础 | 二维码/评估码入口、路由、任务状态、接口封装、错误处理、移动端基础布局 | 患者 Web 工程入口和公共请求层 |
| B | 答题前端量表 | 通用题目组件、SCD-Q9、GDS-15、进度、漏答校验、草稿恢复、提交页 | 量表页面和答题状态管理 |
| C | 答题后端访问 | 令牌与评估码校验、任务读取、题目定义、草稿保存、幂等更新 | 患者公开查询和草稿接口 |
| D | 答题后端计分 | 提交完整性校验、提交事务、两张量表计分器、逐题得分和结果生成 | `Response`、`ScoreResult` 和计分规则 |
| E | 管理前端 | 登录、患者列表、患者详情、创建评估、二维码、报告和统计卡片 | 医生 Web 工程全部业务页面 |
| F | 管理后端基础 | 医生鉴权、患者档案、数据库迁移、公共错误格式、运行配置 | `User`、`Patient` 和数据库结构 |
| G | 管理后端评估 | 创建评估、生成令牌和二维码地址、评估状态、报告查询、统计接口 | `Assessment` 和医生评估接口 |

### 所有权规则

`Assessment` 由 G 负责，其他成员不能自行修改其字段或状态定义：

- G 创建任务并生成访问令牌。
- C 校验令牌、读取任务、保存草稿，并调用统一方法进入 `IN_PROGRESS`。
- D 提交时调用统一方法进入 `SUBMITTED`。
- F 负责迁移文件审核，但不改变业务状态规则。

报告分工：

- D 生成并保存原始计分结果。
- G 将患者、评估和计分结果组合为医生报告和统计接口。
- E 只负责展示，不能在前端重新计分。

### 联调关系

| 联调内容 | 参与人员 |
| --- | --- |
| 二维码、评估码和任务进入 | A、C、G |
| 题目读取、草稿保存和恢复 | B、C |
| 提交、计分和结果生成 | B、D |
| 医生登录和患者档案 | E、F |
| 创建评估和二维码展示 | E、G、A |
| 报告与统计 | E、D、G |

代码评审规则：

- A 与 B 互审答题前端，A 额外评审 E 的请求层。
- C 与 D 互审答题后端。
- F 与 G 互审管理后端。
- 数据结构和状态变更必须由 F、G 共同确认。
- 计分规则变更由 D 实现，并由 C 使用固定样例复核。

管理前端进度落后时，先取消非核心展示效果；答题端核心流程完成后，A 协助 E 处理请求封装，B 协助 E 完成报告答案组件，E 仍是管理前端负责人。

## 9. 开发顺序

### 阶段一：技术和接口冻结

- 调查成员技术能力并确定技术栈。
- 建立两个前端、一个后端和接口契约目录。
- 冻结数据对象、API 字段、错误码和答案编码。
- 确定数据库迁移和本地启动方式。
- 准备计分测试样例。

### 阶段二：模块独立开发

- 完成医生登录、患者档案和评估任务接口。
- 完成患者扫码入口和量表填写。
- 完成管理端档案和评估页面。
- 完成草稿与两张量表计分器。
- 各模块先使用模拟接口或固定数据独立运行。

### 阶段三：闭环联调

1. 医生登录并创建受检者。
2. 创建评估并生成二维码和备用码。
3. 手机 Web 读取任务。
4. 保存和恢复草稿。
5. 提交并计分。
6. 医生查看报告。
7. 首页统计更新。

### 阶段四：程序稳定

- 修复联调问题。
- 补充异常状态处理。
- 完成手机端适配。
- 执行完整回归测试。
- 固化虚拟数据和启动方式。
- 功能冻结后只修复缺陷，不再扩大范围。

## 10. 部署方案

第一阶段默认采用同一局域网演示：

- 患者端、医生端和 API 部署在一台演示电脑。
- 手机与演示电脑连接同一 Wi-Fi。
- 使用统一入口提供：
  - `/patient/`：患者 Web。
  - `/admin/`：医生 Web。
  - `/api/`：后端 API。
- 启动脚本输出局域网访问地址。
- 创建评估时，根据当前访问地址生成二维码。
- Web 服务必须监听局域网地址，不能只监听 `localhost`。

若后续需要异地填写，可改为公网 HTTPS 部署，不修改业务接口。

## 11. 程序验收测试

必须验证：

- 正确密码可以登录，错误密码被拒绝。
- 可以创建和查看受检者。
- 每次创建评估得到唯一令牌和备用码。
- 手机扫码后能够进入正确评估。
- 备用码能够进入同一评估。
- 无效令牌和备用码被拒绝。
- 填写一半退出后能够恢复草稿。
- 网络失败不会静默丢失当前答案。
- 漏答时不能最终提交。
- SCD-Q9 最低 0 分、最高 9 分，含 0.5 分的样例正确。
- GDS-15 最低 0 分、最高 15 分。
- 重复提交不产生第二份结果。
- 提交后不能继续修改答案。
- 医生端能够查看逐题答案和总分。
- 完成评估后统计数据同步更新。
- 患者端在 360、390、430px 宽度下可以正常操作。
- 医生端在 1366×768 下可以完成全部操作。
- 直接刷新任一前端子路由不会返回 404。
- 患者公开接口不能访问其他患者或医生接口。
- 前端不能通过篡改请求指定分数。
- 报告不展示确诊性结论。

## 12. 迭代边界

第一阶段不实现：

- 微信小程序。
- 患者账号和微信授权。
- 其他 A/B/C 级量表。
- CDR、PSQI 和开放式访谈。
- LLM 功能。
- 多医生和多角色权限。
- 真实患者数据。
- 数据导入导出。
- 自动疾病诊断。
- PPT、实践报告和演示视频。

第二阶段可基于现有的量表版本、JSON 答案和独立计分器机制增加更多量表，无需重新设计整个流程。
