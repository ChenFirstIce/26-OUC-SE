# 第一阶段 MVP：小程序量表录入与计分闭环

## 1. MVP 目标

在 2026 年 9 月 17 日前完成以下程序闭环：

```text
医生通过管理 Web 创建受检者与评估
              ↓ 生成评估码
患者通过微信小程序填写量表
              ↓ 服务端保存并自动计分
医生通过管理 Web 查看报告和基础统计
```

首期功能：

- 受检者基础档案。
- SCD-Q9、GDS-15 两张自填量表。
- 评估码进入任务。
- 草稿自动保存和恢复填写。
- 服务端规则计分。
- 医生查看结构化报告。
- 受检者数、完成评估数、两张量表平均分。
- 单一医生演示账号。
- 编号化虚拟数据。

本阶段只聚焦程序设计、开发、测试和运行，不安排 PPT、实践报告、视频等最终交付物。

## 2. 系统结构

系统由患者微信小程序、医生管理 Web、共享后端和数据库组成：

```text
患者微信小程序 ─┐
                 ├── 统一后端 API ── 数据库
医生管理 Web ───┘
```

建议工程边界：

```text
patient-miniapp/  患者微信小程序
admin-web/        医生管理 Web
server/           后端服务
contracts/        API 文档、公共类型和错误码
```

小程序和管理 Web 通过同一个后端 API 和统一接口契约联调。四名后端成员使用同一个后端工程和数据库，不拆分微服务。

## 3. 技术栈确定机制

暂不指定具体前端、后端和数据库框架。开发前根据七名成员的实际经验完成选型。

选型要求：

- 患者端技术能够构建微信小程序。
- 管理端技术支持桌面 Web。
- 后端支持 JSON API 和自动化测试。
- 小程序与管理 Web 可以共享接口类型或 OpenAPI 契约。
- 系统能够在开发和演示环境快速启动。
- 尽量减少团队需要临时学习的新技术。

技术栈确定后，应记录语言、框架、版本、项目结构、启动命令、数据库初始化方式和各工程负责人，本阶段中途不再更换框架。

## 4. 患者微信小程序

### 页面

- 评估码输入页。
- 任务介绍与受检者确认页。
- SCD-Q9 答题页。
- GDS-15 答题页。
- 漏答复核与提交页。
- 提交成功页。

### 主要功能

1. 输入 8 位评估码进入指定任务。
2. 展示受检者代称、量表列表和非诊断提示。
3. 分步骤填写两张量表。
4. 显示题号和总体进度。
5. 选择答案后自动保存草稿。
6. 退出或关闭后恢复未完成答案。
7. 提交前检查漏答并定位题目。
8. 提交后展示成功状态并锁定任务。

评估状态：

- `CREATED`：尚未填写。
- `IN_PROGRESS`：存在草稿。
- `SUBMITTED`：已提交并锁定。

交互要求：

- 选项和按钮尺寸适合老年用户点击。
- 每页只显示一题或少量题目。
- 网络失败时保留本地答案并提示重试。
- 不向患者展示疾病诊断结论。

首期不实现患者注册、微信授权、手机号登录、消息通知和患者报告查询。

## 5. 医生管理 Web

### 页面

- 登录页。
- 基础统计页。
- 受检者列表和创建页。
- 受检者详情及评估历史页。
- 创建评估页。
- 评估状态页。
- 答案及计分报告页。

### 主要功能

- 单一医生账号登录。
- 创建和查看受检者档案。
- 创建评估并生成 8 位评估码。
- 查看评估状态。
- 查看逐题答案和量表总分。
- 展示受检者数、完成评估数和量表平均分。

受检者档案只包含编号、代称、性别、出生日期、受教育年限和备注。

管理端保持 MVP，不实现复杂图表、批量操作、导入导出、多医生权限和精细动画。

## 6. 后端与数据设计

### 核心数据对象

- `User`：单一医生账号和密码摘要。
- `Patient`：受检者基础档案。
- `Assessment`：受检者、评估码、状态、量表版本和时间。
- `Response`：量表编号、版本、JSON 答案和更新时间。
- `ScoreResult`：总分、逐题得分、计分版本和生成时间。

答案采用可扩展结构：

```json
{
  "scaleCode": "SCD_Q9",
  "scaleVersion": "1.0",
  "answers": {
    "Q1": "YES",
    "Q2": "NO"
  }
}
```

评估码使用排除易混淆字符的 8 位安全随机字符串，提交后失效。

### 医生端 API

- `POST /api/auth/login`
- `GET /api/patients`
- `POST /api/patients`
- `GET /api/patients/{id}`
- `POST /api/patients/{id}/assessments`
- `GET /api/assessments/{id}`
- `GET /api/assessments/{id}/report`
- `GET /api/dashboard/summary`

### 小程序 API

- `POST /api/public/assessments/resolve`：使用评估码进入任务。
- `GET /api/public/assessments/{code}`：读取任务、题目和草稿。
- `PUT /api/public/assessments/{code}/responses`：幂等保存草稿。
- `POST /api/public/assessments/{code}/submit`：校验、计分并提交。

统一错误码：

- `INVALID_CODE`：评估码无效。
- `ASSESSMENT_SUBMITTED`：评估已经提交。
- `INCOMPLETE_RESPONSES`：存在未答题目。
- `UNAUTHORIZED`：医生未登录或登录失效。
- `VALIDATION_ERROR`：字段格式错误。
- `NETWORK_ERROR`：保存请求失败。
- `INTERNAL_ERROR`：服务端异常。

最终提交必须在同一事务内完成答案保存、计分、结果保存和状态更新，前端不得提交或修改分数。

## 7. 计分规则

### SCD-Q9

- 第 1、2、3、6、8、9 题：“是”1 分，“否”0 分。
- 第 4、5、7 题：“经常”1 分，“偶尔”0.5 分，“从未”0 分。
- 总分范围：0–9。

### GDS-15

- 回答“是”计分：2、3、4、6、8、9、10、12、14、15。
- 回答“否”计分：1、5、7、11、13。
- 每项命中计 1 分，总分范围：0–15。

计分只允许在后端执行。首期只展示分数和逐题结果，不自动诊断 AD 或抑郁程度。

## 8. 七人模块分工

采用“答题前端 2 人、答题后端 2 人、管理前端 1 人、管理后端 2 人”的分配。

| 人员 | 模块 | 主要职责 | 明确所有权 |
| --- | --- | --- | --- |
| A | 小程序入口 | 评估码输入、页面路由、任务状态、接口封装、异常提示和小程序基础配置 | 小程序入口和公共请求层 |
| B | 小程序量表 | 通用题目组件、两张量表、进度、漏答校验、草稿恢复和提交 | 量表页面和答题状态管理 |
| C | 答题后端访问 | 评估码校验、任务读取、题目定义、草稿保存和幂等更新 | 患者公开查询和草稿接口 |
| D | 答题后端计分 | 提交校验、提交事务、计分器、逐题得分和结果生成 | `Response`、`ScoreResult` 和计分规则 |
| E | 管理前端 | 登录、患者列表、患者详情、创建评估、报告和统计卡片 | 管理 Web 全部业务页面 |
| F | 管理后端基础 | 医生鉴权、患者档案、数据库迁移、错误格式和运行配置 | `User`、`Patient` 和数据库结构 |
| G | 管理后端评估 | 创建评估、生成评估码、评估状态、报告查询和统计接口 | `Assessment` 和医生评估接口 |

### 所有权规则

`Assessment` 由 G 负责：

- G 创建任务并生成评估码。
- C 校验评估码、读取任务、保存草稿，并调用统一方法进入 `IN_PROGRESS`。
- D 提交时调用统一方法进入 `SUBMITTED`。
- F 审核数据库迁移，但不改变状态规则。

报告分工：

- D 生成并保存原始计分结果。
- G 组合患者、评估和计分结果，提供医生报告和统计接口。
- E 只负责展示，不能在前端重新计分。

### 联调关系

| 联调内容 | 参与人员 |
| --- | --- |
| 评估码和任务进入 | A、C、G |
| 题目读取、草稿保存和恢复 | B、C |
| 提交、计分和结果生成 | B、D |
| 医生登录和患者档案 | E、F |
| 创建评估和评估码展示 | E、G、A |
| 报告与统计 | E、D、G |

每个人负责本模块的实现、测试和联调。A 与 B、C 与 D、F 与 G 分别互相评审；数据结构变更由 F、G 共同确认，计分规则由 D 实现并由 C 使用固定样例复核。

## 9. 开发顺序

### 阶段一：技术和接口冻结

- 确定技术栈和微信小程序开发方式。
- 建立小程序、管理 Web、后端和接口契约目录。
- 冻结数据对象、API 字段、错误码和答案编码。
- 配置小程序开发环境和后端请求地址。
- 准备计分测试样例。

### 阶段二：模块独立开发

- 完成医生登录、患者档案和评估任务接口。
- 完成小程序评估入口和量表填写。
- 完成管理端档案和评估页面。
- 完成草稿接口与两张量表计分器。
- 各模块先使用模拟接口或固定数据独立运行。

### 阶段三：闭环联调

1. 医生登录并创建受检者。
2. 创建评估并生成评估码。
3. 小程序读取任务。
4. 保存和恢复草稿。
5. 提交并计分。
6. 医生查看报告。
7. 首页统计更新。

### 阶段四：程序稳定

- 修复联调问题。
- 补充异常状态处理。
- 完成小程序真机适配。
- 执行完整回归测试。
- 固化虚拟数据和启动方式。
- 功能冻结后只修复缺陷，不再扩大范围。

## 10. 部署与运行

第一阶段以开发和课程演示为目标：

- 管理 Web、后端和数据库运行在演示环境。
- 小程序通过开发版或体验版访问后端。
- 后端请求地址通过环境配置管理，不写死在业务代码中。
- 若微信平台要求合法域名，则使用可用的 HTTPS 测试地址；开发阶段可使用开发者工具允许的调试配置。
- 准备统一启动说明，确保管理端和后端能够快速运行。

## 11. 程序验收测试

必须验证：

- 正确密码可以登录，错误密码被拒绝。
- 可以创建和查看受检者。
- 每次创建评估得到唯一评估码。
- 无效评估码不能读取任务。
- 小程序退出后能够恢复草稿。
- 网络失败不会静默丢失当前答案。
- 漏答时不能提交。
- SCD-Q9 最低 0 分、最高 9 分，含 0.5 分的样例正确。
- GDS-15 最低 0 分、最高 15 分。
- 重复提交不产生第二份结果。
- 提交后不能继续修改答案。
- 医生端能够查看逐题答案和总分。
- 完成评估后统计数据同步更新。
- 小程序在常见手机尺寸和微信开发者工具中正常操作。
- 患者公开接口不能访问其他患者或医生接口。
- 前端不能通过篡改请求指定分数。
- 报告不展示确诊性结论。

## 12. 迭代边界

第一阶段不实现：

- 患者账号和微信授权。
- 其他 A/B/C 级量表。
- CDR、PSQI 和开放式访谈。
- LLM 功能。
- 多医生和多角色权限。
- 真实患者数据。
- 数据导入导出。
- 自动疾病诊断。
- PPT、实践报告和演示视频。

第二阶段可基于现有量表版本、JSON 答案和独立计分器机制增加更多量表，无需重新设计整个流程。
